# Part 2.3: Concurrency Prevention During Point Conversion

To prevent a user from converting the same points twice under concurrent requests, the conversion flow enforces a two-tier defense: **client idempotency** and **atomic conditional decrement inside a multi-document ACID transaction**. When a conversion request arrives, it requires a client-generated `idempotencyKey` that is written to a unique-indexed field in the conversion record. Within a MongoDB session transaction, the user's point balance is decremented using an atomic query filter: `PointWallets.findOneAndUpdate({ userId, availablePoints: { $gte: pointsToConvert } }, { $inc: { availablePoints: -pointsToConvert } }, { session })`. Because MongoDB acquires an exclusive write lock on that single document for the duration of the operation, two simultaneous conversion requests cannot both pass the `$gte` condition; the first request atomically decrements the points, and the second request immediately fails to match the query filter (`matchedCount === 0`), causing the transaction to abort with `INSUFFICIENT_POINTS`. The same transaction atomically increments the user's cash `Wallets.balance` and appends immutable records to both `PointTransactions` and the cash `Ledger` (with `walletLedgerId` linking them), guaranteeing that points and cash can never double-spend, desynchronize, or drift.
